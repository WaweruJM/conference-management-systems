# RCA — run 0dd7ce1d-5668-4b16-886c-887352211ba2 (scms-platform-1)

## Outcome
Deploy **failed** at `build_image` (Cloud Build step #2 `docker-build`). This is a **source-code fault** — a manifest/pipeline retry will NOT fix it. E1 must apply a source fix and re-trigger the deploy.

## What actually failed (not the headline error)
The `error_message` / `log_excerpt` surfaced by the pipeline points at step #0 `restore-pip-cache`:
```
CommandException: No URLs matched: gs://emergent-default-customers-code/cache/scms-platform-1/pip-cache.tar.gz
```
**This is a red herring** — a cold pip-cache miss. It is non-fatal noise (the cache simply doesn't exist yet for this deployment). Same line appears in past runs. It is NOT the root cause.

The **real** failure is later, inside step #2 `docker-build`, during `yarn build` (Next.js production build):
```
#21  Creating an optimized production build ...
#21  ✓ Compiled successfully in 15.5s
#21    Linting and checking validity of types ...
#21    Collecting page data ...
#21 18.70 Error: SECURITY: JWT_SECRET is missing or too weak (min 32 chars, not dev_secret/changeme). Refusing to start.
#21 18.70     at .next/server/app/api/[[...path]]/route.js:124:76188
#21 18.70 > Build error occurred
#21 18.70 [Error: Failed to collect page data for /api/[[...path]]]
ERROR: executor failed running [/bin/sh -c ... yarn build]: exit code: 1
```

## Root cause
The catch-all API route module `app/api/[[...path]]/route.js` (source: `app/api/[[...path]]/route.(js|ts)`) runs a **JWT_SECRET validation at module import time** — a top-level `throw new Error("SECURITY: JWT_SECRET is missing or too weak ... Refusing to start.")`.

During `next build`, the "Collecting page data" phase **imports and evaluates every route module** to statically analyze it. The Cloud Build environment has **no runtime secrets** (`JWT_SECRET` is injected into the K8s pod at runtime, not into the build), so the top-level check throws and aborts the build.

This is a regression: the previous successful build was `c54d1530` (2026-07-27). The current source introduced (or tightened) this import-time hard-fail check, which is incompatible with Next.js build-time page-data collection.

## Fix (source — E1 to apply)
Do NOT run the JWT_SECRET hard-validation at module top level. Defer it to request time, or skip it during the build phase. Options (pick one), in the API route file that owns the check (and any shared auth/config module it imports at top level):

1. **Move the check inside the request handler** (preferred):
   ```js
   // remove the top-level throw
   export async function GET(req) {
     assertJwtSecret();   // validate here, per-request, at runtime
     ...
   }
   // ...same for POST/PUT/etc. or a shared middleware
   ```

2. **Skip validation during the production build phase:**
   ```js
   if (process.env.NEXT_PHASE !== 'phase-production-build') {
     assertJwtSecret();
   }
   ```

3. **Force the route to be dynamic so it isn't evaluated for static page-data collection** (only if lazy handler-time validation is also kept):
   ```js
   export const dynamic = 'force-dynamic';
   ```

The goal: `next build` (page-data collection) must not execute the JWT_SECRET throw; the validation should still run at runtime so a genuinely missing/weak secret still refuses to serve requests. Also ensure `JWT_SECRET` (>=32 chars, not `dev_secret`/`changeme`) exists as a deployment secret so the runtime check passes once the build succeeds.
